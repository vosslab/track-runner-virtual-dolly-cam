### Behavior or Interface Changes

- **`crop_min_size` removed: torso_height_multiple is now the only zoom knob.** The processing config silently raised crop height to `crop_min_size` source-pixels (default 480) whenever the requested `torso_multiple x torso_h` was smaller. For long-lens footage where the runner is small in the source frame (e.g. tracked torso ~20 px tall), a request of `torso_height_multiple=5` produced the same crop as `torso_multiple=10` because the floor dominated -- exactly the "hidden variable breaking the user's setting" pattern the project tries to avoid. Removed every `crop_min_size` / `min_crop_size` knob from [tr_crop.py](../track_runner/tr_crop.py): `direct_center_crop_trajectory` no longer reads `crop_min_size`; `CropController.__init__` no longer accepts the kwarg; `fixed_height_override` and `slow_size_override` no longer accept it; the YAML default config no longer sets it. A 1-pixel sanity floor is retained internally (so containment-radius division and integer rounding don't fail on a degenerate zero-size crop when the runner sits exactly on a frame edge), but it is not user-facing. Tests in [test_tr_encode_mode.py](../tests/test_tr_encode_mode.py) updated to drop the obsolete key. Migration: existing per-video configs may still set `crop_min_size`; the value is now ignored. Users who relied on the floor as a "don't zoom past N pixels" cap should lower their `torso_height_multiple` instead.

- **Crop zoom now averages width-driven and height-driven estimates of the desired crop size.** Previously `direct_center_crop_trajectory` derived crop height from torso height alone (`desired_crop_h = raw_h * torso_height_multiple`). When the tracked torso bbox was wide-and-short or tall-and-narrow on a given frame, the crop ignored the orthogonal dimension entirely. New behavior: compute two estimates of the desired crop height -- (a) `raw_h * torso_height_multiple` and (b) `(raw_w * torso_height_multiple) / aspect_ratio` -- and use their average. Both estimates use the same `torso_height_multiple` knob, so a torso whose W:H matches the canonical aspect ratio produces an identical answer either way; averaging just makes the zoom robust to either dimension being noisy on a given frame (e.g. arms-out widens raw_w without changing the runner's actual size). [tr_crop.py](../track_runner/tr_crop.py) `direct_center_crop_trajectory` now reads both `state["w"]` and `state["h"]` per frame.

- **Default crop size smoothing turned ON to prevent zoom bouncing.** `crop_post_smooth_size_strength` previously defaulted to `0.0` (disabled), so per-frame torso-bbox jitter (typically +/-5%) translated directly into visible breathing in the encoded crop -- the historical "zoom bouncing" complaint. New code default in [tr_crop.py](../track_runner/tr_crop.py) is `0.15` (forward-backward EMA alpha; ~6-7 frame time constant), and the YAML default config now declares the same value explicitly so fresh setups get the smoothing. Users can still set `crop_post_smooth_size_strength: 0.0` in per-video config to opt out. The existing second-pass re-fit in Step 3.6 already prevents the EMA from lifting any frame past its `_max_centered_fit_size` bound, so smoothing cannot reintroduce off-frame crops.

### Fixes and Maintenance

- **Encode-mode velocity arrow: removed length cap and integer truncation.** Two coupled bugs after a self-review during the `--bin N` rollout. (1) Increasing `_VELOCITY_GAIN` from 3.0 to 9.0 produced no visible change because `draw_debug_overlay_cropped` capped arrow magnitude at `0.5 * w * scale_x` (half the torso-box width in crop-space). For typical sprinting footage with a 5-frame look-back, raw frame-to-frame motion exceeds the cap at every gain >= 1, so the gain was effectively dead. Fix in [encoder.py](../track_runner/encoder.py): drop the cap entirely and remove `_VELOCITY_FALLBACK_CAP_FRAC`; `_VELOCITY_GAIN` is now the only length knob, so doubling it visibly doubles the arrow length. Glitched-frame protection from the original commit is unnecessary because the look-back window already bounds how far back `prev_center` can sit. (2) The arrow angle snapped to ~10-15-degree steps because both endpoints were rounded to integer crop-space pixels in `_point_to_crop_coords` (lines 308-310) and the crosshair was rounded again at lines 554-555. With dx/dy as small integers (typically 1-5 px at 60 fps with a 5-frame look-back on a slow runner), `atan2` only takes a handful of discrete values. Fix: `_point_to_crop_coords` now returns floats; the velocity-arrow block computes both the tail (current crosshair) and head (prev-projected) in floats end-to-end and rounds to int only at the `cv2.arrowedLine` call. The crosshair draw still uses int from `_box_to_crop_coords` (its integer-pixel rounding is desired for cv2.line clarity). The arrow tail is now `round(_point_to_crop_coords(cx, cy, ...))` rather than the box-corner-derived `cross_cx/cy`, so it sits on the true float center even when the box edges have rounded to even/odd pixels.

- **Encode mode: velocity arrow now loads the active per-hash camera-motion cache.** [cli.py](../track_runner/cli.py) `_mode_encode` was calling `camera_motion.load_motion_cache(default_camera_motion_path(input_file))` -- the legacy single-file path -- to build the SceneTransform that projects `prev_center` from camera-relative to land-relative coordinates. After a `--bin N` solve the active cache lives in `<video>.track_runner.camera_motion/<motion_model>_<config_hash>.npz` and the legacy file may be absent or stale, which would silently degrade the arrow to camera-relative motion (or fall back to the "no camera_motion cache available" warning). Switched to `camera_motion.load_active_camera_motion_or_fail(args.input_file)`, which reads the `active.json` marker and resolves to the per-hash file (with a built-in legacy fallback for pre-marker runs). Wrapped in try/except RuntimeError because encode is read-only and degrades gracefully with a warning rather than the hard error refine uses.

- **GUI scene-transform loader: use the active camera-motion identity, not the legacy single-file path.** [base_controller.py](../track_runner/ui/base_controller.py) `_load_scene_transform_for_gui` had the same bug as encode mode: it probed only `default_camera_motion_path` so a video solved with `--bin > 1` would always show the "camera motion not compensated" disclosure badge even when a valid per-hash cache existed. Switched to `load_active_camera_motion_or_fail(video_path)` with try/except so fresh videos (no marker, no legacy file) still return identity and the badge fires correctly. Removed the now-unused `tr_paths` import. Updated the docstring to describe the active-marker path instead of the legacy file.

- **`solver_workers._worker_init` always uses FrameReader.** The init path branched on `bin_factor`: bin=1 used `video_io.VideoReader` (no `.geometry` attribute), bin>1 used `FrameReader` (has `.geometry`). Workers therefore exposed a different reader interface depending on the run's bin, which is the kind of inconsistency that becomes a silent bug when future code calls `reader.geometry` and gets `AttributeError` only at certain bin settings. Switched to `FrameReader` unconditionally; `bin_factor=1` short-circuits the resize and is byte-identical to the legacy `VideoReader` path on the hot read code. Removed the now-unused `import video_io` from `track_runner/solver_workers.py`. The user-facing `VideoReader` class is unchanged and still serves the GUI / encoder.

- **Stale docstrings about the legacy single-file camera-motion path corrected.** `tr_paths.default_camera_motion_path` docstring now describes itself as the backward-compat / diagnostic-tools path (the production loader is `camera_motion.load_active_camera_motion_or_fail`); `camera_motion.save_motion_cache` docstring's `cache_path` argument now documents the per-hash production path with the legacy single-file path noted as still supported.

## 2026-05-01

### Additions and New Features

- **`--bin N` pre-binning at the frame-reader boundary (solve and refine only).** New `--bin N` flag on the `solve` and `refine` subcommands lets the user opt into running the camera-motion (Stage 1) and residual-motion (heat map / `observe_blob_at`) stages on a downsampled copy of every frame. The bin is applied at the I/O boundary inside [frame_reader.py](../common_tools/frame_reader.py): `FrameReader(..., bin_factor=N)` resizes by 1/N (`cv2.INTER_AREA`) and snaps each scaled axis to the largest FFT-friendly "goodbox" not exceeding it, cropping only from the right and bottom edges so the top-left origin stays fixed and coordinate conversion is pure scale. The goodbox predicate (cryo-EM rules: prime factors `<= 11`; alignment grows with size) lives in new module [goodbox.py](../common_tools/goodbox.py) with `is_good_size(n)` and `largest_goodbox_at_most(n)` helpers. Coordinate ownership: `FrameGeometry` (a frozen dataclass on the reader) owns `source_to_processed`, `processed_to_source`, `source_to_processed_delta`, `processed_to_source_delta`. `camera_motion` runs phase correlation on processed frames and upscales `dx`/`dy` to source-frame pixels via `processed_to_source_delta` before constructing `MotionTrack`, so `MotionTrack.dx`/`dy` keep their existing source-frame contract. `residual_motion.observe_blob_at` keeps a source-frame public API: it accepts source-frame `pred_center`/`pred_box`, converts to processed-frame on entry, runs ROI/blob extraction in processed-frame, and converts the centroid plus `cross_track`/`along_track` back to source-frame at exit before constructing `BlobObservation`. The internal raw-blob cache key is renamed `raw_blobs_processed` to make the processed-frame contract explicit at the read site. `target` and `edit` modes do **not** accept `--bin` (per plan: they consume pre-built motion / annotations and stay source-frame only). bin_factor=1 (default) short-circuits the resize path and is byte-identical to the pre-bin reader. A 10% per-axis safety floor caps surprise pixel loss; goodbox crop is disabled on either axis when it would cross the floor (one-line `warnings.warn`). Cache policy: no `SCHEMA_VERSION` bump and no on-disk schema change. **Per-hash camera-motion caches** -- each `(estimator config + bin_factor + processed_width + processed_height)` writes to its own NPZ file under `<video>.track_runner.camera_motion/<motion_model>_<config_hash>.npz`, so a `solve --bin 4` run does not overwrite the higher-quality cache from a prior `solve --bin 1`. Solve writes a small `active.json` marker inside the cache directory pointing at the cache file the current solved state binds to. **Refine never recomputes Stage 1**: it reads the `active.json` marker and loads that exact cache file via `camera_motion.load_active_camera_motion_or_fail(input_file)`; missing marker / missing cache file -> hard error "Camera-motion cache for this solve is missing. Run solve first." Refine still accepts `--bin` for per-frame residual operations in Stages 4-5, but the `--bin` value passed to refine has no effect on the camera-motion track. The interval cache key (`compute_interval_fingerprint`) is **bin-invariant** -- per-frame bin-aware computations cross the source<->processed boundary independently inside `camera_motion` and `residual_motion`, upscaling back to source-frame before the interval solver consumes them, so changing `--bin` between solve and refine reuses the interval cache. Backward compatibility: a pre-bin run that wrote the legacy single-file `<video>.track_runner.camera_motion.npz` is still loaded when its embedded `config_hash` matches today's hash; a missing-marker refine falls back to the legacy file when present. Plan: `~/.claude/plans/federated-knitting-tome.md`. New tests: `test_goodbox.py`, `test_frame_reader_bin.py`, [test_tr_camera_motion_bin.py](../tests/test_tr_camera_motion_bin.py), [test_tr_residual_motion_bin.py](../tests/test_tr_residual_motion_bin.py), [test_tr_interval_fingerprint_bin.py](../tests/test_tr_interval_fingerprint_bin.py), `test_tr_frame_reader_fast_path.py`. **Sequential read fast-path (Stage 1 prerequisite).** During implementation, FrameReader at `bin=1` regressed Stage 1 wallclock by ~15x vs the legacy `VideoReader` because every `read_frame` issued a `cv2.VideoCapture.set(POS_MSEC, ...)` call, which on H.264 mp4 forces a per-frame keyframe re-seek. The legacy `VideoReader` had a `_next_frame` tracker that skipped `set(...)` on consecutive reads; FrameReader did not. Restored as a 10-line strategy-0 in `read_frame`: when `frame_index == self._cap_next_index`, call `cap.read()` directly with no `set(...)`. Strategies 1-5 invalidate the tracker on any scattered access so the fast-path self-disarms. ### Fixes and Maintenance

- **Motion-cue heat map is now fps-aware; restores hot spots on 120 fps daughter clip.** Symptom: on a 120 fps clip (`TRACK_VIDEOS/Lyra-Wheeling-IMG_3912.MOV`) the residual-motion heat map showed no hot spots and `observe_blob_at` returned `None` everywhere, silently degrading the propagator to pure Hermite even though the input was otherwise clean. Root cause was structural: the background-rejection window was a fixed `DEFAULT_HALF_WINDOW = 4` (9 frames), inherited from `tools/diagnose_residual_motion.py`. At 60 fps that span is ~150 ms; at 120 fps it collapses to ~75 ms. The 120 fps daughter clip's slower runner moves only ~0.028 m/frame (vs ~0.11 m/frame for the 60 fps varsity son clip), so within a 9-frame window the runner's pixels overlap heavily across all 8 neighbors. The `nanmedian` then absorbs runner pixels into the background estimate and `abs(target - median)` collapses near zero. Fix: replace the constant frame count with a temporal window resolved per call. New helper `track_runner.residual_motion.resolve_half_window(window_seconds, fps, min_half_window=2, max_half_window=12)` converts seconds + fps to a frame count via `round(window_seconds * fps / 2)`, clamped to `[2, 12]`. ## 2026-04-27

### Additions and New Features

- **Velocity arrow now shows land-relative motion, not camera-relative.** The encode-mode `--draw-velocity-arrow` overlay was computing the arrow direction from the runner's pixel-space (camera-frame) center between consecutive frames. When the camera panned faster than the runner moved on the ground, that subtraction produced a vector pointing *opposite* the runner's ground motion -- a misleading visualization. Fixed by projecting each prior frame's pixel position through scene (land-anchored) coordinates via `scene_coords.SceneTransform` and back into the *current* frame's pixel coords; the arrow drawn from the current crosshair to that reprojected point now reflects ground motion expressed in the current camera's pixel space. The driver-side prev_center precomputation in [cli.py](../track_runner/cli.py) `_mode_encode` loads `camera_motion.load_motion_cache(default_camera_motion_path(...))` once before the per-frame loop; falls back to the previous camera-relative behavior with a one-line warning if the cache is unavailable (run `solve` to populate it). The encoder code is unchanged -- it still consumes `state["prev_center"]` per frame; the projection happens entirely on the driver side, so parallel workers see correct land-relative arrows at every frame including chunk seams.

- **Centered-fit follow-up: velocity cap conflicts with centered contract; unused parameter removed.** Reviewer found that `direct_center_crop_trajectory` Step 6 (per-frame velocity cap on the crop center, gated by `crop_post_smooth_max_velocity > 0`) recomputes the crop center after the new fit step ran, which both decentred the runner (the lagged crop center no longer equals the runner's smoothed scene position) and could re-introduce a black-fill edge (the lagged crop may overshoot a source edge that the fit step had avoided). The user's stated contract is "keep torso centered at all costs", which trumps post-fit motion smoothing. Fixed in [tr_crop.py](../track_runner/tr_crop.py) by skipping Step 6 when `crop_centered_fit_to_source` is true. Reviewer also flagged an unused `desired_h` parameter in `_max_centered_fit_size`; removed it from the signature and updated the helper's call sites in `direct_center_crop_trajectory` and the test suite. The other reviewer concern (floor application could break aspect) is a false alarm: since `_max_centered_fit_size` returns aspect-preserving (fit_w, fit_h) and `floor_w = floor_h * aspect`, fit_w < floor_w iff fit_h < floor_h by simple algebra, so when one floor binds both bind and the result preserves aspect; a comment in the code documents this.

- **`crop_mode: direct_center` keeps the runner centered by shrinking the crop to fit the source frame.** Per user direction "torso_multiple is the ideal/cap, keep torso centered, do best crop possible. Previously, direct_center mode let the crop window slide off the source frame and produced encoded video with black bars (and the runner pinned to one side) when the requested zoom did not fit centered on the runner -- the failure mode the new pre-flight validator was catching as `OffCenterCropError`. New behavior: the user-specified `torso_height_multiple` is the *maximum zoom-out*, not a fixed target. Per frame, the crop is shrunk (preserving aspect) until at least one edge of the crop touches a source-frame edge, with the runner staying at the output center. Effective zoom-out varies smoothly across the video as the runner moves through different frame regions; the existing `crop_post_smooth_size_strength` (forward-backward EMA on the crop-height signal) handles the breathing, with a second-pass smoothing applied after the fit step so the EMA cannot lift a frame back over the bound. New helper `tr_crop._max_centered_fit_size(cx, cy, desired_w, desired_h, frame_width, frame_height, aspect_ratio)` returns the largest aspect-preserving (w, h) centered on (cx, cy) that fits inside the source frame. Behavior is controlled by a new processing-config flag `crop_centered_fit_to_source` with default `true`; setting it to `false` reverts to the legacy black-fill path for users who want it. The previous validator (`OffCenterCropError`, `--allow-offcenter-crop`) stays in place as a safety net for the legacy path and for unusual cases (runner exactly at a frame edge where the min_crop_size floor binds). - **Encode-mode pre-flight gate: refuse to encode when the runner leaves the safe central crop window.** A user-reported bug surfaced where aggressive `--torso-multiple 8 --aspect '23:9'` with a 1280x500 output produced an encoded video showing the runner pinned to the right edge with the left ~70% black-filled. ### Fixes and Maintenance

- **`max_tasks_per_child=1` on the solver pool** in [solver_workers.py](../track_runner/solver_workers.py) `make_pool`. Every interval is now solved in a fresh worker process that exits and is replaced after the task returns. Hard upper bound on per-worker memory growth: when a process exits, the OS reclaims the entire heap, pymalloc arenas, numpy buffers, and OpenCV decode state, so no leak source -- found or undiscovered -- can survive a single interval. Followed up after the LRU cap on `_read_gray_frame` reduced the RSS climb but did not fully arrest it (drift to 15 GB across 7 workers at 11/100 intervals), and Explore-agent search of the solver/transform/numpy paths surfaced additional unbounded caches (BGR frame entries co-located with the gray cache via `cache[("bgr", fi_other)]` at `residual_motion.py:516-523`, plus pymalloc arena stickiness keeping retired allocations resident even after `dict.clear()`). Per-interval recycle bypasses all of these mechanically: solving a single interval has a deterministic upper memory bound, and that bound is what RSS stays at. Costs ~1-3 s of process spawn + module import + WorkerContext pickle per interval, which is < 5% overhead on this video's tens-of-seconds-per-interval solve. Python 3.11+ supports the keyword directly on `concurrent.futures.ProcessPoolExecutor`. Tests: 27 solver tests pass, pyflakes clean.

- **LRU cap on the per-interval grayscale frame cache** in [residual_motion.py](../track_runner/residual_motion.py) `_read_gray_frame`. New module constant `MAX_GRAY_CACHE_FRAMES = 24` placed alongside `DEFAULT_HALF_WINDOW`. The cache dict is now treated as an LRU: hits re-insert to mark the entry as most-recently-used (insertion-order tail), misses insert and then evict from the front until size is at or below the cap. Root cause confirmed by `_temp_solve_watch.sh` on `Lyra-Hersey-800m-IMG_3882.MOV`: with `iosurface_count` flat (no IOSurface leak), `wired_mb` flat (no kernel leak), `parent_fds` flat (no FD leak), but `kids_rss_kb` climbing monotonically from 0 to 21.7 GB across 7 worker processes while only 1/101 intervals had completed -- a Python-heap leak in the workers, not an OpenCV C-side leak. At 2816x1584 float32, each cached frame is ~17.8 MB; long intervals visited hundreds of frames per worker (interval_length + 16 entries per worker) and 7 workers x ~9 GB peak overran 36 GB of RAM, causing macOS to panic and reboot during `re-solve.sh` batch runs (twice). The intended boundary was `interval_solver.solve_interval_analytical` which allocates `residual_cache = {}` and clears it after FWD/BWD finish, but a single long interval was already large enough to OOM before that boundary fired. `compute_residual_for_frame` only needs the half_window=4 -> 9-frame neighborhood of the current frame, and the FWD/BWD passes walk frames sequentially in a predictable direction; a 24-entry LRU caps memory at ~430 MB/worker (~3 GB across the pool) without re-decoding any frame in the active rolling window. Tests: 24 residual tests, 50 solver-adjacent tests, 112 lint tests pass.

- M2 Stage-1 race-start detector rewritten to use windowed directional-coherence normalized by torso width (contract C1) in [race_start.py](../track_runner/race_start.py) `locate_race_start_bracket`. The earlier `displacement_per_s` pairwise metric did not work on real clips: dense pre-race annotations at adjacent frames produced huge per-second values from 1-2 pixel annotation jitter, triggering the bracket inside the stationary cluster. ### Decisions and Failures

- Solve-queue refactor -- `solve_queue` is intentionally a domain-specific name, not a generic `queue_manager` or `interval_dispatch` abstraction. The module IS solver interval orchestration -- making that honest in the filename discourages future feature creep into a general-purpose queue layer that this codebase does not need.
- Solve-queue refactor -- [interval_fingerprint.py](../track_runner/interval_fingerprint.py) is locked to fingerprint + seed-filter only. A future patch that adds `race_phase`, `erasure`, or other "intrinsic-to-an-interval" helpers to this module is a regression -- a catch-all low-level module is how premature abstraction starts. New helpers belong in their own file or stay in `interval_solver.py` until a concrete third caller exists.
- Solve-queue refactor -- `ExecutionContext` holds immutable run configuration only (reader, transforms, fps, paths, worker count, debug). No accumulators, no progress-bar handles, no mutable state. Future features that need a shared mutable must pass it explicitly as a kwarg; smuggling state through the context is rejected at review.
- Solve-queue refactor -- the function-level import of `solve_interval_analytical` inside `execute_interval_work` is a tactical compromise, not an endpoint. The clean ownership story is "queue owns execution AND solve implementation lives in a module the queue imports at module load." Moving `solve_interval_analytical` is out of scope for this refactor; the comment at the import site documents it as such. Do not propagate the pattern to new symbols.
- Solve-queue refactor -- fingerprint drift between solve and refine modes was the primary risk this refactor mitigates. Before: two independent fingerprint walks had to agree; adding a queue invariant required editing two files and proving they still agreed. After: `plan_interval_work` is the single source of truth, and `test_fingerprints_unchanged_by_parallel_refactor` in `test_solver_parallelism.py` locks the bytes.
- The empty-track hover bug visible in the user's reference frame (FWD, fused, and BWD torso boxes over an empty curve while the real runners were ~100 px to the right) was diagnosed as solver drift, not a fusion gap. The purely-kinematic analytical propagator consulted no image evidence; seeds 100 px left of truth were interpolated to more of the same. The previous fix (motion-cue fusion as a post-process) addressed the symptom by snapping to blobs globally, but its cross-frame memory (`prev_accepted_blob`, `miss_count`, temporal chains) re-introduced drift through the back door and made refine O(total frames). This patch series moves correction into the propagator itself as a stateless, local, three-outcome operation (blend, ignore, fall through), keeps the local temporal window bounded to `{t-1, t, t+1}` computed from `raw_pred` only, and deletes the chained code so it cannot regress. Design philosophy and invariant list live at the top of `~/.claude/plans/happy-forging-valiant.md`.
- Post-audit, five corrections were applied to the initial blob-snap landing. (1) Temporal-smoothness gate: the original spec `dist(blob, raw[t-1] + v_prev) < beta * |v_prev|` algebraically collapsed to `dist(blob, raw[t]) < beta * |v_prev|` (velocity-scaled proximity), not a true motion-path check. Replaced with `_motion_path_ok()` in [velocity_model.py](../track_runner/velocity_model.py): decomposes `blob - anchor` into along-motion and perpendicular components and rejects blobs that sit off the motion line (perpendicular > `PATH_PERP_FRACTION * |v|`) OR outside the forward segment (`proj` not in `[0, |v| * (1 + PATH_SLACK)]`). Both neighbors (raw[i-1] with `v_prev` and raw[i+1] with `-v_next`) must pass when their motion magnitudes exceed the velocity floor. (2) Removed the dead blob-coverage severity tie-breaker from [review.py](../track_runner/review.py): `severity == "low"` required `agreement >= 0.40` while the tie-breaker guard required `agreement < 0.30`, so the rule never fired. Coverage remains a pure diagnostic. (3) Split the aggregated `blob_coverage_fraction` into per-pass `blob_coverage_fwd` and `blob_coverage_bwd` in [interval_solver.py](../track_runner/interval_solver.py) `_coverage_from_track` and `_stamp_blob_coverage`; aggregation hid FWD/BWD asymmetry which is exactly the signal the dual-scoring design wants preserved. (4) Added explicit documentation to `observe_blob_at` noting the ROI-coupling caveat (first caller at a frame sets the ROI; second caller reuses). (5) Renamed destructured locals inside `_apply_blob_snap` to `raw_cx` / `raw_cy` and introduced separate `snap_cx` / `snap_cy` output locals so the read path (gates) and write path (blend) are typographically distinct. New invariant test `test_raw_pred_is_never_mutated_by_snap` locks the separation. Constants in the solver fingerprint bumped accordingly (`BLOB_SNAP_BETA` -> `BLOB_SNAP_PATH_SLACK` + `BLOB_SNAP_PATH_PERP_FRACTION`).
- Triple-audit round surfaced a HIGH-severity spec deviation and two philosophy refinements. (HIGH) WP-B1 specified `Cache key is a stable tuple of (frame_index, roi_hash)`, but the initial implementation keyed by `frame_index` alone. This silently constrained BWD's candidate blob pool to the ROI FWD picked -- precisely the coupling the dual-scoring philosophy forbids. Restructured `observe_blob_at` in [residual_motion.py](../track_runner/residual_motion.py) to key the cache by `(frame_index, roi)` where `roi` is the ROI tuple itself; the `_frames` sub-cache stays keyed by `frame_index` alone (raw frame bytes are ROI-independent). FWD and BWD with divergent raw_pred now each compute their own residual on the cache-miss path; convergent cases still share one computation. On tight curves and crowd scenes -- the exact regimes this feature targets -- FWD/BWD independence is now structural, not empirical. (Refinement 1) Motion-path gate made asymmetric in [velocity_model.py](../track_runner/velocity_model.py) `_apply_blob_snap`: only `path_ok_prev` is checked. The former symmetric `prev AND next` rule over-rejected valid blobs near upcoming-occlusion edges and curvature where t+1 raw_pred carries accumulated Hermite error. Iteration-order "prev" is always closer to the pass's starting seed and has accumulated fewer propagation steps, so it is the more trustworthy anchor; t+1 disagreement is tolerated by construction. `path_ok_next` computation removed entirely so the asymmetry cannot be misread as accidental. (Refinement 2) ROI tuple is quantized to `ROI_QUANT = 8` px in `_compute_roi`: sub-quantum FWD/BWD jitter collapses into the same cache bucket (avoiding accidental cache fragmentation), while tens-of-pixels divergence produces distinct ROIs. New test `test_roi_quantization_collapses_subpixel_jitter` locks this invariant.

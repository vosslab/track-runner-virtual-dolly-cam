### Additions and New Features

- **`--auto-bin [HEIGHT]` flag added to `solve` and `refine`.** Computes `bin_factor = max(1, round(source_height / target))` from the probed source height (via [common_tools/probe_video.py](../common_tools/probe_video.py)), so a single batch script can target a binned vertical resolution across mixed-resolution inputs without picking a per-video `--bin`. Bare `--auto-bin` defaults to target 480; pass `--auto-bin 720` for 720. `bin_factor` is a whole number, so the actual binned height only approximates the target (e.g. 1080->bin2->540, 2160->bin4->540, 2816->bin6->469, 1540->bin3->513 then goodbox-snapped to 480). At target=720: 1080->bin1 (1080), 1440->bin2 (720), 2160->bin3 (720). Round (not floor) was chosen so `--auto-bin 720` on a 1080-line source actually does what the user typed something larger asks for; concretely floor breaks "--auto-bin 720" on 1080 sources (gives bin=1, no binning). Wired into a mutually exclusive group with `--bin` in [track_runner/cli_args.py](../track_runner/cli_args.py) `_add_bin_arg`; resolved against `video_info["height"]` in [track_runner/cli.py](../track_runner/cli.py) `_run_solver` immediately before the existing `bin_factor >= 1` validation, with a one-line log showing source height, chosen bin, and resulting actual height. [re-solve.sh](../re-solve.sh) updated: both the first-pass `solve --yes` and the second-pass `solve --upgrade` invocations append `--auto-bin` so re-solving a mixed batch (1080p + 4K + 720p sources) hits roughly 540-line working frames without per-video flags.

- **`FrameReader` no longer emits "source_width/source_height is not divisible by bin_factor" warnings.** Non-divisible source dims silently drop at most `(bin_factor - 1)` right/bottom pixels, which is identical in spirit to the goodbox right/bottom crop already applied a few lines later in `_resolve_frame_geometry`. ### Fixes and Maintenance

- **FrameReader scattered-read fix: prefer `POS_FRAMES` over `POS_MSEC`.** Stage 4 blob promotion was stalling for 25+ minutes with 0/47 intervals completed on a 4K H.264 MOV after the `solver_workers` migration to `FrameReader`. Root cause: `read_frame` strategy 1 seeked via `cap.set(CAP_PROP_POS_MSEC, time_msec)`. On H.264 mp4/MOV containers, `POS_MSEC` typically forces a per-call keyframe re-seek; `POS_FRAMES` does not. The S1 validation on the bin plan only measured *sequential* reads (200 consecutive pair reads), where strategy 0's fast-path skips the `set(...)` entirely -- so the cliff was invisible until Stage 4, where `residual_motion.observe_blob_at` builds a temporal neighbor stack around frame `i` (i-N..i+N) per non-endpoint frame and the FWD/BWD passes hit those windows out of order. The legacy `track_runner/video_io.py::VideoReader` always seeked via `POS_FRAMES` (line 88), which is why the pre-migration blob path was fast on the same footage. Fix in [common_tools/frame_reader.py](../common_tools/frame_reader.py): swap strategies 1 and 2 -- strategy 1 is now `POS_FRAMES`, strategy 2 is `POS_MSEC` (kept as fallback for codecs where `POS_FRAMES` does not honor random access). The strategy-0 sequential fast-path is unchanged. All 29 frame_reader tests still pass.

- **Per-interval stationary lock removed end-to-end from the propagator.** `track_runner/velocity_model.py` previously computed `is_stationary = displacement < 0.03 * left_h` between the two interval-bracketing seeds in `fit_interval_curves`, then (a) froze the raw Hermite curve at the left/right seed center and dimensions for the whole interval in `_compute_raw_pred_forward` / `_compute_raw_pred_backward`, (b) carried the flag as the 7th element of the raw-pred tuple, and (c) short-circuited blob-snap on stationary frames in `_apply_blob_snap` while stamping `stationary_lock` into every per-frame `snap_pred` dict. That case is rare and indistinguishable in output from a pure Hermite fit on the same two seeds, since Hermite on near-zero displacement is already effectively flat and the blob-snap velocity-floor branch (`v_pred_mag <= BLOB_SNAP_VELOCITY_FLOOR`) routes such frames through proximity-only acceptance. Deleted: the `is_stationary` computation and dict key in `fit_interval_curves`; the `if is_stationary:` freeze branch in both forward and backward raw-pred builders; the 7th tuple slot (raw-pred is now a 6-tuple `(frame_index, cx, cy, w, h, conf)`); the `or is_stat` short-circuit in the snap-pred loop and the `stationary_lock` key on both `snap_pred` output dicts. `tools/check_interval_blob_funnel.py` and `tools/check_prediction_divergence.py` updated to the new tuple shape; their `is_endpoint or is_stat` skip rule is now just `is_endpoint`. `docs/TR_CONFIG_FILES.md:172` per-frame-extras list drops `stationary_lock`. ### Fixes and Maintenance

- **`--debug-blob` flag relocated from top-level parser to `solve` and `refine` subparsers.** First user invocation of `solve --upgrade --bin 4 --debug-blob` failed with `error: unrecognized arguments: --debug-blob` because argparse subparsers consume all post-subcommand args and reject unknown flags. The original M0a wired the flag onto the top-level parser at the same position as `-d/--debug` (so `--debug-blob solve ...` worked), but every existing subcommand-specific flag in this repo (`--bin`, `--upgrade`, `--full`, `--keep`, etc.) lives on the subparser so users naturally type the diagnostic flag after `solve`. New helper `_add_debug_blob_arg(parser)` in [track_runner/cli_args.py](../track_runner/cli_args.py) registers the flag once; both `solve_parser` and `refine_parser` call it. Top-level registration removed; `set_defaults(debug_blob=False)` removed from the top-level parser. Smoke test [tests/test_tr_debug_blob_flag.py](../tests/test_tr_debug_blob_flag.py) updated to put `--debug-blob` after the subcommand and added a `test_debug_blob_flag_parses_true_on_refine` mirror; 11/11 pass.

- **M3+M4 pre-pass cache-population fix: eliminate residual scattered seeks inside the per-worker pre-pass.** First M3+M4 implementation showed Stage 4 still doing 292 `seek_frame` strategy calls per run despite the architectural fix (~50 per worker per interval). Root cause: two bugs in [track_runner/residual_pre_pass.py](../track_runner/residual_pre_pass.py) `precompute_interval_residuals`. (1) Sliding-window eviction during the sequential walk dropped BGR entries below `fi - half_window - 2`, so by the time the residual-computation loop ran, only the last ~11 frames near `pad_hi` were in cache; every interval frame's neighbors fell through to `reader.read_frame` as scattered seeks. Fix: removed eviction; the entire `pad_lo..pad_hi` BGR range stays in `frame_cache` until the function returns. Memory budget per worker per interval: ~600 MB at bin=4 for a 377-frame interval (well under the 36 GB system budget for 7 concurrent workers). (2) The pre-pass populated only `frame_cache[("bgr", fi)]` (BGR uint8); `_read_gray_frame` in `compute_residual_for_frame` uses integer key `frame_cache[fi]` for grayscale-float32. Every center-frame gray read missed the cache and hit `reader.read_frame` as a scattered seek. Fix: pre-convert each BGR frame to gray-float32 during the walk and store at the integer key. After both fixes the live `--debug-blob` instrumentation shows compute_residual cache hit rate at 16/16 (100%) per call and Stage 4 wall time dropped from "never completes" to 2:52 wall on the user's iPhone HEVC HDR file (58 intervals, P50=65.8 s, P95=135.1 s, max=138.8 s). Plan: `~/.claude/plans/memoized-percolating-moler.md` M3+M4 verification gate.

- **Heartbeat thread snapshots dispatch/complete dicts to avoid concurrent-mutation races.** Found by post-implementation bug-hunt review. The `--debug-blob` heartbeat thread in [track_runner/interval_solver.py](../track_runner/interval_solver.py) iterated `t_dispatch_by_pair` while the main thread concurrently wrote to it on each task submit; in CPython, `dict.__setitem__` during `dict.__iter__` can raise `RuntimeError: dictionary changed size during iteration` (rare at 5-second intervals but possible under load). Same race for `t_complete_by_pair` (writes at completion vs `in` membership reads in heartbeat). Fix: snapshot both dicts at the top of the heartbeat loop body via `dict(dispatch_map)` and `dict(complete_map)` before iterating. The heartbeat thread is daemon=True so a crash there was silent (printing just stops); the fix preserves the diagnostic output reliability through full Stage 4 runs.

- **M2 trailing call-site fixes in `compute_heat_map_roi` consumers.** The M2 stride migration removed `window_seconds` from `compute_heat_map_roi`, but three call sites still passed it: [track_runner/ui/heat_map_overlay.py](../track_runner/ui/heat_map_overlay.py) `_compute_and_display`, the patched `_stub_residual` in [tests/test_tr_residual_motion_bin.py](../tests/test_tr_residual_motion_bin.py), and the direct call in [tests/test_tr_residual_heat_map.py](../tests/test_tr_residual_heat_map.py) `test_facade_output_is_roi_scoped_not_full_frame`. All three updated to drop the kwarg; the `_stub_residual` signature swapped `window_seconds=None` for `stride=None` to match the production signature post-M2. After the fix repo-wide `tests/test_tr_*` pass 562/562.
